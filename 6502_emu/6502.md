## What this folder contains

This folder is the start of a 6502 emulator. The current implemented component is
`Bus`, in `bus.h` and `bus.cpp`. It owns a 64 KiB array and provides methods to
read and write bytes and to copy a list of program bytes into memory. `cpu.h` is
currently empty, so CPU instructions and registers are not implemented here yet.

## C++ types and declarations

### Fixed-width integer aliases

`bus.h` includes `<cstdint>` and defines:

```cpp
typedef std::uint8_t u8t;
typedef std::uint16_t u16t;
```

`std::uint8_t` is an unsigned integer exactly 8 bits wide; `std::uint16_t` is
unsigned and exactly 16 bits wide. These sizes match common 6502 data: one-byte
values and 16-bit memory addresses. `typedef` gives those existing types shorter
names for use in the emulator. The newer equivalent syntax is `using u8t =
std::uint8_t;`, but the current `typedef` form is valid C++.

An unsigned 8-bit value can represent 0 through 255 (`0x00` through `0xFF`), and
an unsigned 16-bit value can represent addresses 0 through 65,535 (`0x0000`
through `0xFFFF`).

### Header directives

`#pragma once` tells supported compilers to include this header at most once in
a compilation unit. This prevents duplicate declarations when multiple files
include `bus.h`.

The lines beginning with `#include` make declarations from standard library
headers available: `<array>` provides `std::array`, and `<cstdint>` provides the
fixed-width integer types. These directives are processed before C++ compilation.

### Class declarations and access

`class Bus { ... };` declares a type named `Bus`. The final semicolon is required
after a class definition. Members following `public:` can be called by other
code; members before a `public:` label are private by default. The current
`ram` array is public, so other code can access it directly as well as through
`read` and `write`.

`Bus();` declares the constructor, which runs when a `Bus` object is created.
`~Bus() = default;` declares the destructor and asks the compiler to generate
its normal behavior. The array does not require custom cleanup.

### `std::array`

```cpp
std::array<u8t, 64 * 1024> ram;
```

`std::array` is a fixed-size container whose element count is part of its type.
Here it stores 65,536 (`64 * 1024`) bytes, which is 64 KiB. `ram` is the member
name. Array indexes start at zero, so its valid indexes are 0 through 65,535.
Unlike a raw C-style array, `std::array` provides helpers such as `.fill()` and
`.size()` while keeping the storage fixed-size.

## The bus

The bus is the path the CPU uses to access memory and, in a fuller emulator,
other devices. Its interface is declared in `bus.h`; the definitions in
`bus.cpp` use `Bus::method_name` to indicate that each function belongs to the
`Bus` class. `#include "bus.h"` makes that class declaration available to the
implementation file.

### Construction and initialization

```cpp
Bus::Bus() {
	ram.fill(0);
}
```

This is the constructor definition. `ram.fill(0)` assigns zero to every byte
in the array when a `Bus` is constructed. This gives the emulated memory a
deterministic initial value; it does not model a particular 6502 machine's
power-on RAM contents.

## Reading and writing memory

### Read

The declaration is:

```cpp
u8t read(u16t addr, bool readonly = false);
```

It returns one byte (`u8t`), accepts a 16-bit address (`addr`), and has an
optional Boolean argument. The `= false` is a default argument: callers may
write `read(address)` and the compiler supplies `false`, or pass an explicit
second argument such as `read(address, true)`. The current implementation does
not inspect `readOnly`, so the argument has no effect yet.

The definition checks `addr < ram.size()`. If true, it returns `ram[addr]`; if
false, it returns `0x00` (a hexadecimal byte literal for zero). In the current
design, `addr` can hold 0 through 65,535 and `ram.size()` is 65,536, so this
condition is always true. The fallback is therefore unreachable with these
types and this full-size RAM array. It may become useful if the memory layout or
address handling changes.

### Write

```cpp
void write(u16t addr, u8t data);
```

`void` means the method does not return a value. The implementation stores
`data` in `ram[addr]` when the same bounds check succeeds. As with `read`, the
check is always true for the current 16-bit address and 64 KiB array, so every
possible address currently refers to ordinary RAM.

## Loading a program

The method declaration is:

```cpp
void load_program(const std::initializer_list<u8t>& program, u16t start_addr);
```

`std::initializer_list<u8t>` lets a caller provide a short list of byte values,
for example `{0xA9, 0x01}`. `const ...&` passes that list by reference without
copying it and prevents the method from changing the list. `start_addr` is the
memory address at which the first byte is stored.

The definition starts a local address counter at `start_addr`, then uses a
range-based `for` loop (`for (u8t byte : program)`) to visit each byte in order.
For each one, `write(addr++, byte)` stores it and then increments `addr` for
the next byte. The postfix `++` expression uses the current address for this
write and increments it afterward. The method does not currently check whether
the sequence wraps past `0xFFFF`; because `addr` is 16-bit, incrementing past
that value wraps to `0x0000`.

## Address decoding and future hardware

The comment in `bus.cpp` asks about checking whether an address belongs to RAM
or a PPU range. That decision is called **address decoding**: the bus examines
the address and routes the access to the appropriate memory region or device
instead of treating every address as ordinary RAM.

The current bus is not yet a specific console or computer memory map. It has a
full 64 KiB RAM array, so every 16-bit address goes to RAM. For a system with a
PPU or other memory-mapped devices, the bus would need that system's address-map
specification. It could then route ranges to RAM, device registers, or ROM, and
apply any required mirroring rules. The exact ranges and mirroring behavior
depend on the target machine; they should not be guessed from the 6502 CPU alone.

When implementing that map, both reads and writes need the same routing rules,
with device-specific behavior where appropriate. The `readOnly` parameter may
be useful for debugger or inspection reads that must not trigger device side
effects, but it currently has no defined behavior in this implementation.

### Example: NES address map

The mention of a PPU suggests an NES-like system, but the project has not yet
declared the target machine. If the target is the original NES, its CPU address
space is divided into regions rather than backed by 64 KiB of ordinary RAM:

| CPU addresses | Typical destination | Mapping note |
| --- | --- | --- |
| `0x0000`-`0x1FFF` | 2 KiB internal RAM | The 2 KiB repeats four times; use `addr & 0x07FF` as the RAM index. |
| `0x2000`-`0x3FFF` | PPU registers | The 8 registers repeat every 8 bytes; use `addr & 0x0007` as the register index. |
| `0x4000`-`0x4017` | APU and controller I/O | Route to the appropriate audio or input device. |
| `0x4018`-`0x401F` | Disabled/test area | Behavior is generally not ordinary RAM. |
| `0x4020`-`0xFFFF` | Cartridge space | Reads and writes depend on cartridge hardware; ROM writes are not RAM writes. |

The bitwise AND (`&`) masks off address bits that select a mirrored copy, so
different CPU addresses can reach the same small backing store. For example,
`0x0800 & 0x07FF` is `0`, meaning the first RAM byte is mirrored at `0x0800`.

This sketch shows the shape of a read dispatcher, not code that can be pasted
into the current `Bus`: it assumes a 2 KiB RAM array and a PPU object that do
not exist yet.

```cpp
if (addr <= 0x1FFF) {
	return ram[addr & 0x07FF];
}
if (addr <= 0x3FFF) {
	return ppu.read_register(addr & 0x0007);
}
```

A real NES bus also needs to handle the remaining ranges and write behavior.
Keep read and write decoding consistent, and route each range to its actual
device instead of silently treating it as RAM. If this emulator targets a
different 6502-based machine, use that machine's memory map instead; a 6502 CPU
does not define a PPU or a universal device map.
